# ADR 0004: v1 data model choices

**Status:** Accepted (v1, 2026-11). Items marked "v2" are expected to change.

## Context
v1 needs only organizations and their first admin, but every later feature hangs off these two tables, so tenancy must be designed in from the start.

## Decisions
1. **Tenant = organization.** `users.organization_id` is a non-null foreign key (`ON DELETE CASCADE`, indexed). Every future table gets an organization reference.
2. **UUID primary keys**, generated by Postgres (`gen_random_uuid()`), so ids cannot be guessed or counted from outside. Cost: slightly larger indexes.
3. **Email is globally unique and stored lowercase** (lowercased in the application). Login needs only email and password. A per-organization unique email would require asking for the organization at login.
4. **`role` is a plain column** with a CHECK constraint allowing only `admin`. **v2 replaces it** with roles and permissions tables.
5. **Timestamps are `timestamptz`, set by the database** (`now()`). `updated_at` refreshes only for changes made through SQLAlchemy.
6. **Schema changes go through Alembic migrations only**, never `create_all()`. Tests build their schema with the same migrations.

## Alternatives considered
- Auto-increment integer ids: simpler, but enumerable.
- Schema-per-tenant or database-per-tenant: stronger isolation, much more operational work. Not needed yet.
- Designing the full permission model in v1: premature, since v2 will show what it needs.

## Consequences
- A user belongs to exactly one organization. Supporting one person in several organizations would need a join table (revisit if required).
- Case-insensitivity depends on the application lowercasing emails. A functional unique index on `lower(email)` would enforce it in the database too.
- The `role` column needs a small migration in v2.
